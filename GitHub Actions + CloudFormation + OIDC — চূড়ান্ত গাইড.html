চূড়ান্ত সংস্করণ: পুরো লাব একবার করে, যেখানে যেখানে আটকেছি আর যা শিখেছি, সব এখানে যোগ করা।

এই লাবে আপনি নিজে AWS-এ গিয়ে কোনো সার্ভার বানাবেন না। শুধু git push করবেন, বাকিটা GitHub Actions নিজে করবে। প্রতিটা ধাপে আছে কী করবেন, কেন, আর ভিডিওতে কী বলবেন।

অ্যাসাইনমেন্ট থেকে যা বদলানো হয়েছে Region: README-তে লেখা "us-west-2 (N. Virginia)", কিন্তু N. Virginia আসলে us-east-1। আমরা us-east-1 ব্যবহার করছি। deploy.yml-এ Region কোডে লেখা নেই, সেটা vars.AWS_REGION থেকে আসে। তাই শুধু GitHub variable-এ us-east-1 দিলেই হবে। শুধু cleanup-এর CLI কমান্ডে us-west-2 লেখা আছে, নিচের গাইডে সেটা ঠিক করা।
OIDC subject: README-তে নতুন রিপোর subject ফরম্যাট নিয়ে যা লেখা আছে সেটা ঠিক। GitHub-এর অফিশিয়াল ঘোষণা অনুযায়ী ১৫ জুলাই ২০২৬-এর পরে বানানো রিপোতে subject হয় repo:OWNER@OWNER_ID/REPO@REPO_ID:ref:refs/heads/main।

১. আপনার মানগুলো বসান

মানগুলো বসালে নিচের trust policy, API লিংক, Role ARN আর git কমান্ড নিজে থেকেই তৈরি হবে। Owner ID আর Repo ID পাবেন Step 2-এ।

এই মানগুলো শুধু আপনার ব্রাউজারে থাকে, কোথাও পাঠানো হয় না।

২. ভিডিও রেকর্ডিং প্ল্যান

এই লাবে blur লাগবে বেশি জায়গায় Account ID আসবে কনসোলের উপরের ডানদিকে, trust policy-তে, Role ARN-এ, GitHub-এর Variables পেজে, আর Actions log-এর "Confirm AWS identity" ধাপে। এই ধাপ নিজেই Account আর ARN প্রিন্ট করে। EC2-র public IP লাব শেষে মুছে যাবে, তাই সেটা দেখালে সমস্যা নেই।

জেনে রাখুন: রিপো Public হলে Actions-এর log-ও পাবলিক থাকে, অর্থাৎ যে কেউ "Confirm AWS identity"-র আউটপুটে আপনার Account ID দেখতে পারবে। Account ID নিজে কোনো password বা key না, আর এর সাথে কোনো credential প্রকাশ পায় না, তাই এটা লাবের ক্ষেত্রে মেনে নেওয়ার মতো। তবে চাইলে জমা দেওয়ার পর পুরনো workflow run-গুলো মুছে দিতে পারেন (Step 14)।

কখনো স্ক্রিনে আনবেন না: AWS access key, secret, GitHub token, password।

৩. আর্কিটেকচার আর OIDC কীভাবে কাজ করে

OIDC সহজ ভাষায় পুরনো পদ্ধতিতে AWS-এর স্থায়ী access key GitHub Secrets-এ রাখতে হতো। সেই key কখনো ফাঁস হলে, সেটা বাতিল না করা পর্যন্ত যে কেউ আপনার অ্যাকাউন্টে ঢুকতে পারত।

OIDC-তে কোনো key রাখা হয় না, কাজ হয় এভাবে:
  1. Workflow চলার সময় GitHub একটা সই করা টোকেন (JWT) তৈরি করে। এই টোকেনে লেখা থাকে কোন repo, কোন branch থেকে এটা এসেছে (sub), আর কার জন্য (aud = sts.amazonaws.com)।
  2. Runner সেই টোকেন AWS STS-কে দেয় (AssumeRoleWithWebIdentity)।
  3. AWS তিনটা জিনিস যাচাই করে: (ক) টোকেনটা আসলেই GitHub-এর সই করা কিনা, যার জন্য IAM-এ OIDC provider লাগে; (খ) aud মেলে কিনা; (গ) sub হুবহু আপনার repo আর main branch-এর সাথে মেলে কিনা, যেটা trust policy-তে লেখা থাকে।
  4. সব মিললে AWS প্রায় ১ ঘণ্টার জন্য একটা অস্থায়ী credential দেয়, যা নিজে থেকেই মেয়াদ শেষে অকেজো হয়ে যায়।
অর্থাৎ চুরি করার মতো কোনো key কোথাও জমা থাকে না। অন্য কোনো repo বা অন্য branch থেকে চেষ্টা করলে sub মিলবে না, তাই AWS ঢুকতে দেবে না।
একটা উদাহরণে OIDC অফিসে একজন ডেলিভারি ম্যান আসে। পুরনো পদ্ধতি (access key): তাকে অফিসের একটা স্থায়ী চাবি দিয়ে দেওয়া। চাবি হারালে বা কেউ কপি করে নিলে, তালা না বদলানো পর্যন্ত যে কেউ ঢুকতে পারবে। OIDC পদ্ধতি: সে আসে কোম্পানির সিল-মারা পরিচয়পত্র নিয়ে। রিসেপশন আগে থেকেই কোম্পানির সিল চেনে, আর তার কাছে একটা তালিকা আছে কোন দোকানের লোক ঢুকতে পারবে। সব মিললে তাকে দেয় ১ ঘণ্টার ভিজিটর পাস।

কেনএই ধাপে AWS-কে বলে দেওয়া হচ্ছে যে GitHub-এর সই করা টোকেন বিশ্বাসযোগ্য। AWS এখন GitHub-এর public key দিয়ে টোকেনের সই যাচাই করতে পারবে। একটা অ্যাকাউন্টে এই provider একবারই লাগে। পরে GitHub-এর অন্য কোনো প্রজেক্টও এটা ব্যবহার করতে পারবে।


প্রশ্নোত্তর: provider URL আর audience
URL কেন https://token.actions.githubusercontent.com? এটা GitHub Actions-এর issuer, মানে টোকেন যে তৈরি করে তার অফিশিয়াল পরিচয়। প্রতিটা টোকেনে লেখা থাকে "iss": "https://token.actions.githubusercontent.com"। AWS এই URL-এর সাথে /.well-known/openid-configuration যোগ করে সেখানে যায়, আর GitHub-এর public key কোথায় আছে সেটা খুঁজে বের করে (jwks_uri)। GitHub টোকেনে সই করে নিজের private key দিয়ে, আর AWS সেই সই যাচাই করে public key দিয়ে। ভিডিওতে চাইলে https://token.actions.githubusercontent.com/.well-known/openid-configuration ব্রাউজারে খুলে দেখাতে পারেন, এটা খোলা তথ্য।


Audience কেন sts.amazonaws.com? aud মানে টোকেনটা কার জন্য বানানো। এখানে টোকেন গ্রহণ করে AWS STS (AssumeRoleWithWebIdentity)। এই নিয়মের কারণে Azure বা অন্য কোনো সার্ভিসের জন্য বানানো GitHub টোকেন এনে AWS-এ ব্যবহার করা যায় না।


এগুলো কি সবসময় একই? GitHub.com থেকে AWS-এ গেলে প্রায় সবসময় একই। URL বদলায় টোকেন কে বানাচ্ছে তার উপর: GitHub Enterprise Server-এ https://HOST/_services/token, আর GitLab-এ https://gitlab.com। Audience হলো configure-aws-credentials action-এর ডিফল্ট মান। বদলাতে চাইলে তিন জায়গায় একসাথে বদলাতে হবে: provider, trust policy আর workflow।


সংক্ষেপে: Provider যাচাই করে টোকেনটা আসলেই GitHub-এর কিনা। Trust policy ঠিক করে কোন repo আর কোন branch ঢুকতে পারবে। Permission policy ঠিক করে ঢোকার পর কী কী করা যাবে।


ভিডিওতে বলুন"এখানে AWS-কে শেখাচ্ছি GitHub-এর টোকেন কীভাবে চিনতে হয়। তবে কে ঢুকতে পারবে, সেটা এখানে ঠিক হচ্ছে না। সেটা ঠিক করবে পরের ধাপের role।"

তবুও এটা production-মানের না: EC2-এর জন্য Resource: "*" দেওয়া, অর্থাৎ এই role অ্যাকাউন্টের যেকোনো EC2 মুছতে পারবে। Production-এ resource বা tag দিয়ে সীমা টানা হয়, CloudFormation service role ব্যবহার করা হয়, আর ডিপ্লয়ের আগে অনুমোদন (approval) নেওয়া হয়।


আমাদের অভিজ্ঞতা: Next বাটন কাজ করছিল নাJSON ঠিক ছিল আর Errors 0 দেখাচ্ছিল, কিন্তু নিচের Security / Errors / Warnings লেখাগুলো ধূসর হয়ে ছিল। মানে validator তখনো যাচাই শেষ করেনি। এই ক্রমে চেষ্টা করুন:

  2. উপরে স্ক্রল করে দেখুন প্রথম লাইন শুধু { কিনা। ডিফল্ট টেমপ্লেট না মুছে পেস্ট করলে দুটো { থেকে যায়।
  3. Visual ট্যাবে গিয়ে আবার JSON-এ ফিরে আসুন।
  4. এডিটরে Ctrl+A, তারপর Delete, তারপর আবার পেস্ট করুন।
  5. Next চাপার পর পেজের উপরে স্ক্রল করে কোনো লাল error banner এসেছে কিনা দেখুন।

কেন StringEquals, wildcard নাsub-এ * দিলে (যেমন repo:*) GitHub-এর যেকোনো রিপো আপনার AWS-এ ঢুকতে পারত। হুবহু মিলিয়ে (StringEquals) দেওয়া মানে শুধু এই একটা রিপো, আর শুধু main branch। কেউ অন্য branch-এ push করলেও role পাবে না।
